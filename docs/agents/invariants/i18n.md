# UI localisation (i18n)

The UI follows the **VS Code display language** (`vscode.env.language`), the same value
`spinney.replyLanguage = auto` already follows. Two shipped languages besides English:
Simplified Chinese (`zh-Hans`) and Traditional Chinese (`zh-Hant`). Any other display
language falls back to English — a missing catalog is never an error.

## One catalog per language, keyed by the English string

```
package.nls.zh-Hans.json         ← the manifest catalog (package.json only)
package.nls.zh-Hant.json
l10n/bundle.l10n.zh-Hans.json    ← the runtime catalog (host + webview)
l10n/bundle.l10n.zh-Hant.json
package.nls.json                 ← the English manifest values (identity mapping)
```

Following VS Code's own convention, **the key is the English source string** (with
`{0}` / `{1}` placeholders), so nothing has to be named twice and a translator sees
the sentence they are translating. English needs no file at all: the source strings
*are* the English catalog, and an unknown key returns the source.

## The file names are canonical; the copies VS Code reads are generated

The repo names a catalog by its **canonical, region-invariant** tag — `zh-Hans`, never
`zh-cn`. VS Code cannot: the language packs still declare the legacy region id
(`vscode-language-pack-zh-hans` carries `"languageId": "zh-cn"`), so
`vscode.env.language` is `zh-cn` / `zh-tw`, and that reported tag is the name **both**
of VS Code's own lookups use —

```
l10n/bundle.l10n.<tag>.json    the host strings, read by VS Code for `vscode.l10n.t`
package.nls.<tag>.json         the manifest strings, read by VS Code for `%key%`
```

— and neither lookup knows about scripts. The bundle is looked up by exact name, with
no fallback at all; the manifest strips one hyphen-segment at a time
(`package.nls.zh-cn.json` → `package.nls.zh.json` → `package.nls.json`). A catalog
named `zh-Hans` is therefore invisible to both, and a `package.nls.zh.json` fallback
would feed Simplified Chinese to a Traditional window, which is worse than English.

So the canonical names are what the repo authors, the reported-tag names are what gets
shipped, and the pair between them lives in exactly one module — `src/languageTags.ts`,
deliberately import-free so the dev scripts can `require` it out of `out/` the way
`check-models.js` requires `out/agent/models.js`. `tools/sync-l10n-aliases.js` writes
the copies:

| Who | When the reported-tag copies exist |
|---|---|
| `npm run sync:l10n` | writes them, byte-for-byte, from the canonical catalogs |
| `vscode:prepublish` | runs it before `vsce` reads the tree (and after `compile`, which it needs) |
| `vscode:prepublish` → `check:l10n` | fails the package when a copy is missing or no longer identical |
| `npm run clean:l10n`, `build-deploy.ps1` (`finally`) | removes them again — after a successful package *and* after a failed one |
| `.gitignore` | lists all four names, so a leftover from an interrupted run cannot be committed |

`vsce` reads `.vscodeignore` only — it never consults `.gitignore` — so a file that is
generated *and* ignored still lands in the `.vsix`; that is the whole trick, and it is
also why the aliases are checked for existence rather than merely tolerated.

Two consequences worth knowing:

- **A build made outside that flow has English manifest and host strings.** Running
  from source (F5) mounts the folder as an extension, so it needs the aliases on disk
  too: that is what `npm run dev` (`compile` + `sync:l10n`) is, and it is the
  `preLaunchTask` of the "Run Extension" configuration.
- **`--locale=zh-Hans` now works**, where before it did not: that window reports the
  canonical tag, which finds the authored file for both lookups, and
  `src/i18n.ts` maps either spelling to the canonical one for its own reader.

## Two lookup paths, one catalog

- **Host** (`src/**/*.ts`): `vscode.l10n.t('Send')`. VS Code resolves the locale
  and reads `l10n/bundle.l10n.<locale>.json` itself. `package.json` contributes
  `%key%` instead, resolved through `package.nls*.json`.
- **Webview** (`media/main.js`): a webview is a plain document with no API bridge,
  so it cannot call `vscode.l10n`. `ChatViewProvider.getHtml()` therefore injects
  the whole catalog as `window.__spinneyL10n` (inline `<script>` with the panel
  nonce) and the webview uses its own `tr(message, ...args)` — same keys, same
  placeholders. `tr()` falls back to the source string, which is also what keeps
  `check:webview` working: that guard loads `media/main.js` with no dictionary on
  purpose.

`readCatalog()` in `src/i18n.ts` is the only place that reads a
`l10n/bundle.l10n.<locale>.json` file directly (it caches its one read per window
behind `webviewL10n()`, and `l10nDiagnostics()` re-uses the same reader for its
found/not-found line). `ChatViewProvider.getHtml()` and `ModelPanel.getHtml()` only
*consume* it: each injects the dictionary into its own page. `<html lang="…">` is the
display locale.

## The guard

`npm run check:l10n` (`tools/check-l10n.js`, in `vscode:prepublish`) extracts every
key from the code — `vscode.l10n.t('<literal>'`, `tr('<literal>'`, and `%key%` in
`package.json` — and fails the build when

1. a string used in the code has no entry in a shipped catalog (silent English),
2. an entry is no longer used (a reworded string leaving a stale translation),
3. a translation's `{0}` / `{1}` placeholders differ from its source,
4. a `package.nls.<locale>.json` key set differs from `package.nls.json`,
5. a `%key%` in `package.json` does not resolve (or is unused), or
6. a generated alias (`package.nls.zh-cn.json`, `l10n/bundle.l10n.zh-tw.json`, …) is
   missing, or is no longer byte-identical to the canonical catalog it copies.

Rule 6 is not about a translation at all: it is the guard against shipping a `.vsix`
whose host and manifest are English while its webview is Chinese. `sync:l10n` runs
first in `vscode:prepublish`, so a missing alias there means the packaging flow itself
was changed — and running `npm run check:l10n` by hand says which command to run.

Because of the extractor, **a translatable message must be a single string literal,
passed as the first argument** — never concatenated, never a template literal. Use
placeholders and let the translation reorder the sentence:

```ts
vscode.l10n.t('Delete {0} sessions?', n)                 // yes
vscode.l10n.t(`Delete ${n} sessions?`)                   // no — invisible to the guard
'Delete ' + n + ' sessions?'                             // no
```

## What is deliberately *not* translated

- **Brand and identifiers**: `Spinney`, command ids, setting ids, model ids
  (`deepseek-flash`), tool names, `harness`, currency codes.
- **Model- and control-plane-facing text**: tool results, tool-argument validation
  errors, prompt text (`src/agent/prompt.ts`, `src/chat/sessionTitles.ts`),
  HTTP responses, `{ ok: false, error: … }` payloads. The language the *agent*
  answers in is `spinney.replyLanguage`, a different knob; translating what the
  model reads would silently change tool behaviour and the prompt cache.
- **Diagnostics**: the Spinney output channel (`[config]`, `[migrate]`, `[layout]`,
  `[perf]`) and `perf()` lines — they are read by a developer, not a user, and
  grepping them is part of debugging.
- **Protocol values that are also UI strings**: a status that the webview *also*
  compares or uses as a CSS class. The webview keeps the value and translates only
  the displayed text (`el('span', 'tool-status running', tr('running'))`), and it
  never re-translates a payload the host already localized (`msg.status`,
  `msg.text`).
- **Compact dock tokens**: `ctx`, `bal`, `tok/s`, `SUB`, `BG` and the glyph buttons
  (`▶`, `✕`, `🗑`) stay Latin/token-like — they are pinned to a fixed-width
  readout whose layout is a fixed-width px grid, and their explanatory
  `title` tooltips *are* translated.
- `spinney.replyLanguage.enumDescriptions`: those are the language names exactly as
  the prompt carries them (see `agent/languages.md`-adjacent note in
  `invariants/config-keys.md`), so the dropdown must keep reading like the prompt.

## The `'New session'` sentinel

A session's provisional title is *stored data*: `chat/runtime.ts` recognizes "nobody
has named this yet" by comparing the stored title, and `chat/tree.ts` /
`chat/sessionTitles.ts` write a default when a record carries no title. Those two
modules are pure data (no `vscode`, unit-testable outside the Extension Host), so
they keep the English sentinel; the host reads it through
`defaultSessionTitle()` / `isDefaultSessionTitle()` (`src/i18n.ts`), which accepts
both spellings. A bare `session.title === 'New session'` in host code is a bug on
any non-English window: the session would silently stop being auto-named.

## Adding a string or a language

- New UI string: write it as a literal inside `vscode.l10n.t(...)` / `tr(...)`, add
  it to every `l10n/bundle.l10n.*.json`, run `npm run check:l10n` (it names anything
  missing).
- New language: add `l10n/bundle.l10n.<locale>.json` + `package.nls.<locale>.json`
  (copy an existing one, translate the values), named by the language's **canonical**
  tag. If VS Code reports a *different* tag for that language — the Chinese packs
  report the region ids, and that is the only case today — add the pair to
  `src/languageTags.ts` and `npm run sync:l10n` takes care of the rest. Nothing else:
  the guard picks the new files up from the directory listing. Ship it in the `.vsix`
  (`.vscodeignore` does not exclude `l10n/` or `package.nls*.json`).
- Check the `[i18n]` line in the **Spinney** output channel: it names the display
  language the host resolved, the canonical catalog it reads, and the reported-tag
  copy VS Code reads for the host strings — the only way to tell "English because the
  window is English" from "English because the catalog name is wrong" or "…because the
  package was built without its aliases".
